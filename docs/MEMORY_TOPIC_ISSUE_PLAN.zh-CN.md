# MemoSync Issue 计划：自定义主题与批量归类

本计划按照最新讨论调整优先级：以用户自定义记忆主题为主线，批量归类服务于主题整理；“本会话不学习”是附属需求，记忆反馈统计留待后续。

本文用于向上游维护者提需求和讨论方案，尚未实现或提交 issue。此前的[记忆功能改进提案](./MEMORY_IMPROVEMENT_PROPOSALS.zh-CN.md)保留为背景材料，当前范围与优先级以本文为准。

## 一、范围与优先级

| 优先级 | 需求 | 要解决的问题 | 预期贡献 |
| --- | --- | --- | --- |
| 主线，首先交付 | 自定义主题、按主题浏览、单条及批量归类 | 用户难以按自己的习惯整理不断增长的记忆库 | 提高查找和整理效率，让用户掌握分类方式 |
| 附属，独立交付 | 本会话不学习，但继续使用已有记忆 | 临时讨论可能产生不值得保留的候选 | 减少临时信息进入记忆库，不影响其他会话 |
| 后续，不纳入本次验收 | 记忆使用与反馈概览 | 使用次数不足以说明相关性和维护成本 | 为以后调整主题与记忆内容提供可追溯依据 |

主线可以独立成立，不依赖附属需求或反馈统计完成。建议先提交主 issue；附属需求经维护者认可后另开关联 issue。

## 二、主 Issue：支持用户自定义主题与批量归类

### 建议标题

**支持用户自定义记忆主题，并按主题浏览和批量归类**

### 要解决的问题

现有个人、项目和会话范围说明记忆在哪里生效，但用户还需要按内容管理记忆，例如“开发规范”“环境配置”“测试要求”“排错经验”。

当新记忆出现时，用户希望直接选择已有主题，或者输入自己的主题名称并创建。之后的新记忆和已有记忆都应能继续归入该主题。条目积累后，还应能一次整理多条，而不必逐条打开编辑。

项目已有 `topic` 字段，但字段存在不等于已经具备完整的用户主题管理：本提案重点是创建、复用、浏览、重命名和批量归类的完整操作流程。

### 典型使用场景

1. 智能体提议：“修改 API 后需要补充回归测试。”
2. 用户打开该记忆的主题选择框，输入“测试要求”。
3. 如果主题存在，直接选择；如果不存在，点击“创建主题‘测试要求’并归入”。
4. 之后出现“修复问题时先增加复现测试”，用户可直接选择“测试要求”。
5. 用户在记忆看板点击“测试要求”，查看该主题中的条目，并结合项目、状态筛选。
6. 用户勾选几条历史记忆，一次归入“测试要求”，或创建另一个主题并批量归入。

选择主题不自动接受候选。待审记忆归类后仍然待审，是否生效继续由原有审阅流程决定。

### 首版交互与规则

| 功能 | 期望行为 |
| --- | --- |
| 选择主题 | 记忆卡片或详情中提供可搜索的主题选择框 |
| 创建主题 | 支持用户自由输入名称，明确点击“创建并归入”后执行 |
| 复用主题 | 已创建主题持续出现在选择列表中，可供后续记忆使用 |
| 未分类 | 没有主题的条目进入“未分类”，分类不是接受或保存记忆的前提 |
| 主题浏览 | 看板提供“全部”“未分类”与主题列表，点击后筛选条目 |
| 组合筛选 | 主题可以和个人／项目／会话范围、状态等条件组合 |
| 单条调整 | 已有记忆可以改选主题，或移回“未分类” |
| 批量归类 | 勾选多条后，选择已有主题或创建新主题，统一归入 |
| 重命名 | 修改主题名称，关联记忆统一显示新名称 |
| 删除主题 | 明确提示影响数量；删除分类关联，原记忆回到“未分类” |
| 空主题 | 最后一条记忆被移出后，主题仍保留，供以后继续使用 |

首版建议每条记忆最多属于一个主题，采用平级主题列表。深层目录、多个标签和主题合并留到后续讨论。

### 主题与适用范围的关系

**主题用于整理内容，适用范围决定记忆在哪里生效，两者相互独立。**

例如，一条 MemoSync 项目记忆归入“开发规范”后，仍然只按原有项目范围生效，不会因此变成个人记忆。

首版建议当前本地记忆库共用一个主题目录，同一主题可被不同项目的记忆使用。项目筛选只展示属于相应范围的条目，不将其他项目的记忆加入当前任务。

主题名称按既定规范去除首尾空白并检查重复；空名称不允许创建。同名主题应复用，不能因重复点击或并发创建产生多个。具体大小写等匹配规则应统一用于界面、接口和旧数据迁移。

### 批量归类的边界

- 显示选中数量，并明确“全选”是当前筛选结果，不隐式选择整个记忆库。
- 批量操作只调整主题，不顺带改变内容、适用范围或候选状态。
- 操作前校验条目是否仍存在、是否仍允许修改；已拒绝或被并发删除的条目不能被重新激活。
- 完成后分别显示成功、失败和未处理的条目，支持只重试失败项。
- 不允许通过新增主题操作绕过敏感候选原有的审阅约束。
- “创建并批量归入”部分失败时，不重复创建主题，已成功的归类结果应保留并清楚展示。

批量归档、批量接受、拒绝原因和语义合并不属于本次必做范围，可另开后续需求。

### 技术可行性与建议

整体难度预计为中等，主要涉及主题管理界面、批量操作、持久化和兼容旧数据，不需要增加模型调用。

可以先基于现有 `topic` 字段实现选择与筛选，但如果首版包含重命名、删除和空主题，建议使用具有稳定 ID 的独立主题实体，并让记忆关联主题 ID。这样主题改名不必逐条重写内容。

需要特别评估现有 `topic` 的语义：当前它参与记忆内容版本计算，也用于检索。用户管理的分类是否复用该字段，应由维护者决定，不能仅替换字段就假定不会影响模型上下文、历史回滚或导出。

建议实现顺序：

1. 明确主题实体、关联方式，以及旧 `topic` 与用户分类的映射规则。
2. 完成主题创建、查询、重命名、删除和单条归类。
3. 在记忆卡片与看板接入主题选择、列表和筛选。
4. 增加多选与批量归类，沿用或补充统一的服务端校验。
5. 验证旧数据迁移、刷新和重启、失败重试、历史和导出兼容性。

若迁移已有 `topic`：应保留原有分类信息，对重复名称按统一规则处理，没有主题的条目进入“未分类”。迁移应可重复执行而不产生重复主题，也不改变记忆正文、适用范围与状态。分类变更的历史记录和版本策略需单独定义，避免被误认为规则内容修订。

### 预期贡献

- **用户自主性：** 主题名称由用户定义，能匹配自己的项目与工作习惯。
- **整理效率：** 后续条目直接复用已有主题，历史条目支持批量归类。
- **查找体验：** 从主题入口快速定位内容，再按项目和状态缩小范围。
- **行为可预测性：** 分类不改变记忆是否生效及适用范围，降低整理时的误操作风险。
- **后续扩展基础：** 在稳定主题上增加推荐分类、多标签或主题级统计，而不必首版引入这些复杂度。

以上是预期贡献，不代表已经验证的效率提升。

### 验收标准

- [ ] 新候选和允许编辑的已有记忆均可选择已有主题或创建新主题。
- [ ] 新主题在后续操作中可以复用，刷新和重启后仍存在。
- [ ] 归类不会自动接受候选，不修改记忆正文、适用范围或状态。
- [ ] 未分类条目可正常保存和审阅，并能从“未分类”入口找到。
- [ ] 主题筛选可与项目、作用范围和状态筛选组合。
- [ ] 主题重命名后所有关联条目统一显示新名称，空主题也可管理。
- [ ] 删除主题不会删除记忆；受影响条目回到“未分类”。
- [ ] 同名创建、重复提交及并发请求不会产生重复主题。
- [ ] 可以将多条记忆归入已有或新建主题，明确显示操作数量与结果。
- [ ] 部分失败可单独重试，失败不会被显示为全部成功。
- [ ] 原有敏感候选、已拒绝候选和历史恢复规则不被主题操作绕过。
- [ ] 旧分类信息得到兼容，历史和导出中的主题关联不会丢失或失效。

### 后续可讨论的扩展

- 推荐已有主题，但由用户确认，不自动覆盖用户分类。
- 没有合适主题时推荐新名称，由用户确认创建。
- 合并重复主题，并预览受影响条目。
- 根据真实使用需求增加多标签或子主题。

首版不要求模型自动分类、自动生成主题树或自动合并记忆内容。

## 三、附属 Issue：本会话不学习

**建议标题：** 支持当前会话只使用已有记忆，不学习新内容。

### 要解决的问题与贡献

临时排查和试验需要已有项目约定，但不希望产生新的长期记忆。会话级控制可以减少临时候选和后续整理负担，并避免修改全局设置影响其他会话。

### 建议范围

- 在创建会话前或轮次之间选择“本会话不学习”。
- 继续使用已有记忆，不自动生成候选或修改记忆内容；相关后台流程遵守相同限制。
- 设置只作用于当前会话，刷新和重启后保持。
- 当前轮结束后切换，从下一轮生效；全局关闭设置优先。
- 明确聊天记录仍保存，不将该功能称为无痕模式。
- 建议重新开启学习后不补学被排除轮次，并检查学习输入是否包含这些历史内容。

### 核心验收

- [ ] 已有记忆可正常使用，当前会话不会自动生成新候选或内容修订。
- [ ] 后台处理同样遵守限制，其他会话与全局设置不受影响。
- [ ] 设置可持久化，切换生效时间及历史补学规则明确。

此项独立交付，不作为自定义主题功能的完成条件。更详细的边界可参考[此前提案的计划一](./MEMORY_IMPROVEMENT_PROPOSALS.zh-CN.md#计划一会话级关闭学习继续使用已有记忆)。

## 四、后续方向：记忆使用与反馈

本次只记录方向，不纳入实施和验收范围。

待主题功能稳定后，可考虑显示记忆被选择、主动移除、打断纠正和模型审查的记录，以及记忆准备耗时。统计应能追溯到依据，区分用户动作、系统行为和模型判断，不能将引用次数直接解释为实际收益。

如果以后按主题汇总，需要明确记忆换主题前的事件如何归属，避免将历史表现错误地归到新主题。该问题在统计需求阶段单独设计，不阻塞本次主题管理。

## 五、建议提交方式

1. 先以本文件第二部分为依据提交主 issue，重点描述自定义主题与批量归类的使用场景。
2. 将存储方案作为可选实现建议，保留维护者决定内部设计的空间。
3. 将“本会话不学习”列为可关联的独立需求，避免主 issue 同时承担两个系统的改动。
4. 将记忆反馈统计放入后续路线，不以其完成与否判断本次功能是否可交付。
