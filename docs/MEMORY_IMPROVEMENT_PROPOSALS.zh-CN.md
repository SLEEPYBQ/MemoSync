# MemoSync 记忆功能改进提案

本文整理三个适合向上游项目提交 issue 的改进方向。每项均包含要解决的问题、预期贡献、最小实现范围和验收标准，供维护者评估与讨论，不代表已经实现或确定的开发承诺。

方案依据当前仓库的静态代码阅读；难度为相对评估，未经过实现验证。

## 提案概览

| 计划 | 要解决的主要问题 | 预期贡献 | 建议优先级 | 相对难度 |
| --- | --- | --- | --- | --- |
| 会话级不学习 | 临时讨论需要已有记忆，但不希望产生新记忆 | 细化会话控制，减少临时信息进入记忆库 | 高 | 中偏低 |
| 批量记忆维护 | 条目增多后逐条处理成本高，拒绝反馈不够明确 | 降低维护成本，提高反馈的可解释性 | 高 | 基础批量操作中等；语义整理较高 |
| 记忆使用与反馈概览 | 引用次数不足以判断记忆是否相关、是否带来额外负担 | 提供可追溯的使用证据，辅助用户调整记忆 | 中 | 基础统计中等；实际收益评估较高 |

建议分别提交三个 issue。语义分组、按类别屏蔽和实际收益评估作为后续扩展讨论，避免首版范围过大。

## 计划一：会话级关闭学习，继续使用已有记忆

**建议 issue 标题：** 支持会话级关闭记忆学习，同时继续使用已有记忆。

### 要解决的问题

- 临时排查、验证猜想和一次性试验仍需要项目约定，但其中的结论未必值得长期保存。
- 全局关闭学习会影响其他会话；单会话关闭记忆又会同时失去已有记忆的帮助。
- 如果用户只能事后拒绝临时候选，会增加审阅负担，也可能误接受不稳定的信息。

### 当前基础

- 全局记忆设置已经区分“使用记忆”和“从对话中学习”。
- 单会话已有 `memoryDisabled`，用于同时关闭读取和学习。
- 每轮开始时已有 `resolveTurnMemoryState`，计算本轮是否读取、是否学习。

因此，本提案是对现有控制粒度的扩展。建议使用“本会话不学习”的名称，避免“一次性会话”让用户误以为聊天记录不会保存。

### 建议方案与首版范围

1. 在新会话输入区和现有会话中增加“本会话不学习”选项。
2. 保留现有记忆开关；开启“不学习”后，仍可使用已有记忆。
3. 输入区持续显示状态，例如“使用已有记忆 · 不学习新内容”。
4. 选择仅作用于当前会话，并随会话保存，刷新或重启后保持。
5. 只允许在当前轮结束后切换，从下一轮生效。
6. 全局关闭记忆或关闭学习时，会话选项不能越过全局限制重新开启对应能力。

后续可以将界面统一为三种模式：跟随全局设置、只使用已有记忆、关闭记忆。首版不必同时完成这项界面调整。

### 实现要点与边界

- 在会话状态、持久化事件和通信协议中保存学习限制，旧会话默认沿用原有行为。
- 复用每轮记忆状态计算，将会话限制传递到候选提炼、自动修订、维护和迁移等相关流程。
- 不仅隐藏候选界面，还必须阻止后台自动学习和内容变更。
- 可以继续记录已有记忆的使用情况及审查结果，但不能让审查自动触发内容修订；界面应说明这一点。
- 用户在记忆看板中的主动编辑仍按现有规则处理。
- 建议重新开启学习后不补学此前被标记为“不学习”的轮次。实现时需过滤后台学习输入，不能只在写入时检查当前开关。
- 聊天记录仍正常保存。本功能不等同于无痕聊天，也不保证引擎无法通过其他文件写入留下记录。

### 预期贡献

- **用户体验：** 无需反复修改全局设置，即可为临时任务选择合适的记忆行为。
- **记忆质量：** 减少未经验证的临时结论进入长期记忆库的机会。
- **产品一致性：** 在会话层面补齐“读取”和“学习”的独立控制。
- **工程收益：** 延用已有每轮状态机制，集中定义学习权限，便于测试不同引擎的一致行为。

### 验收标准

- [ ] 创建会话前即可选择“不学习”，首轮正确生效。
- [ ] 已有记忆仍可被读取和用于任务。
- [ ] 该会话不会自动产生候选、修订已有内容或迁移出新的记忆。
- [ ] 后台任务与前台操作遵守同一学习限制。
- [ ] 修改本会话设置不影响其他会话和全局设置。
- [ ] 刷新、重启后保留选择；旧会话行为兼容。
- [ ] 重新开启学习不会补学被排除的历史轮次。
- [ ] Claude Code、Codex 和 Pi 的相关路径均得到覆盖。
- [ ] 界面明确说明聊天记录仍会保存。

## 计划二：批量维护记忆，并补充拒绝反馈

**建议 issue 标题：** 支持记忆看板多选及批量归档、拒绝操作。

### 要解决的问题

- 记忆积累到几十或几百条后，逐条归档、拒绝的操作成本较高。
- 相似候选分散展示，用户需要反复阅读和做出相同决定。
- 单纯拒绝无法明确区分“临时信息”“已有规则”和“内容不正确”。
- 用户希望控制重复提议，但拒绝某个具体结论不一定意味着永久屏蔽整个主题。

### 当前基础

- 已有单条归档、候选拒绝、历史记录和部分恢复能力。
- 候选审阅组件由看板与会话审阅入口共享。
- 已有被拒绝候选的内容指纹，用于过滤完全重复的提议。
- 近期非敏感拒绝记录会被提供给模型，用于抑制近似提议；看板已有屏蔽提议列表。

因此，首版重点是提高操作效率，不需要重建拒绝机制。

### 建议方案与首版范围

1. 看板增加多选模式，支持勾选条目和选择当前筛选结果，并显示准确数量。
2. 已生效记忆支持批量归档，待审候选支持批量拒绝。
3. 操作前显示影响范围，完成后分别展示成功、失败和未处理的条目。
4. 支持仅重试失败项，避免重复提交已成功的操作。
5. 沿用现有历史记录、恢复和敏感内容处理规则。

实现可以选择前端批量调用现有接口，或者增加后端批量接口。前者改动较少，后者更便于统一校验和减少重复刷新。Issue 可优先描述期望行为，由维护者选择实现方式。

### 后续扩展

| 扩展 | 建议行为 | 需要控制的复杂度 |
| --- | --- | --- |
| 拒绝原因 | 可选“临时信息”“已有规则”“内容不正确”，默认允许不填写 | 先保存和展示原因，再评估如何用于候选生成；不要把记录反馈等同于模型已学会偏好 |
| 批量调整范围 | 明确选择目标项目或会话，扩大到个人范围时提示影响 | 复用现有范围校验和迁移语义，避免简单修改字段导致错误关联 |
| 相似候选分组 | 先合并展示，保留原文，允许移出分组 | 分组不等于实际合并；内容合并须预览并确认，避免丢失适用条件 |
| 不再提议此类内容 | 单独选择屏蔽范围，默认当前项目，支持查看和撤销 | 不从一次拒绝自动推导永久主题屏蔽；需明确如何匹配“此类内容” |

### 实现要点与边界

- 看板和会话审阅入口使用同一份服务端状态，批量处理后同步刷新。
- 按条目当前状态校验动作，避免已被其他操作处理的候选重复变更。
- 普通归档与敏感候选拒绝的恢复能力不同。敏感内容按现有规则永久删除，不能承诺统一批量撤销。
- 每条成功变更保留审计记录；若引入批量标识，可用于关联同一次操作。
- 如果新增后端批量接口，明确整体回滚还是逐条返回结果；首版建议采用清晰的逐条结果。
- 拒绝原因不得重新保存原本应删除的敏感正文。

### 预期贡献

- **操作效率：** 减少重复点击，降低记忆库规模增长后的维护负担。
- **反馈质量：** 让拒绝决定具有可解释原因，为后续改进提议逻辑提供依据。
- **用户控制：** 将拒绝具体内容与屏蔽某类内容分开，减少误屏蔽。
- **工程收益：** 复用既有领域操作及共享审阅组件，减少不同入口行为不一致的问题。

### 验收标准

- [ ] 可以多选，且清楚区分“当前筛选结果”和“全部记忆”。
- [ ] 已生效记忆与待审候选分别执行正确的归档或拒绝操作。
- [ ] 部分失败不会显示为全部成功，失败条目可单独重试。
- [ ] 重复提交不产生重复变更记录或意外状态跳转。
- [ ] 刷新后状态正确，看板和会话审阅结果一致。
- [ ] 每条操作保留对应历史，遵守原有敏感内容处理规则。
- [ ] 如增加拒绝原因，填写为可选，且历史中能查看原因。

## 计划三：展示可追溯的记忆使用与反馈

**建议 issue 标题：** 增加记忆使用与反馈概览，支持查看统计依据。

### 要解决的问题

- 使用或引用次数不足以说明一条记忆是否相关、是否被正确遵守。
- 用户难以快速识别经常被取消选择、反复需要纠正的规则。
- 记忆准备增加了多少等待时间不够直观。
- 模型自行判断“有帮助”不等于已经证明减少了错误，容易让统计产生误导。

### 当前基础

- 已有记忆使用和审查历史，以及工作记忆选择、排除、打断、恢复等事件。
- 数据分布在记忆 SQLite、会话记录和可关闭的本地使用日志中。
- 不同引擎与历史版本的数据完整性需要核对，不能直接假设现有事件完全适合产品统计。

### 建议方案与首版范围

先在单条记忆详情页增加“使用与反馈”，支持最近 7 天、30 天等时间范围；确认统计口径可靠后，再增加项目级概览。

| 指标 | 建议口径 | 数据性质 |
| --- | --- | --- |
| 选入工作记忆的轮数 | 按会话与轮次去重，区分用户选中与实际交付 | 可观察的系统行为 |
| 用户主动移除次数 | 仅统计明确的移除操作，不将模型未推荐计为拒绝 | 可观察的用户行为 |
| 用户打断并纠正次数 | 根据记忆、打断和恢复记录关联，单独区分仅打断未纠正 | 可观察的用户行为 |
| 记忆审查结果 | 分开展示“违反”“不适用”等结论及证据 | 模型判断，必须标注来源 |
| 记忆准备耗时 | 分开记录计算耗时、人工等待和失败重试 | 可观察的性能数据 |

记忆准备耗时属于会话或轮次指标，可以放在概览和对应轮次详情中，不应将整轮耗时重复归到每条记忆名下。

每项统计应能跳转到支持该数字的会话或历史记录。首版以计数和证据展示为主，不直接给出综合价值分数。

### 实现要点与边界

- 优先从持久化业务记录聚合；对缺少的选择和耗时数据补充最小必要字段。
- 若使用可关闭的日志，明确统计起始时间和覆盖范围；日志关闭或缺失时显示“数据不完整”，不能显示为零次。
- 按事件、轮次和操作标识去重，避免刷新、恢复、重试使计数膨胀。
- 审查失败与没有发现违反不同；无法完成审查的轮次不算成功遵守。
- 记忆内容发生修订时，应能区分版本或标注统计包含旧版本，避免让旧内容的问题被误归到新内容。
- 准备耗时需明确并发阶段的计算方式。用户等待采用实际经过时间，不能简单累加并行任务耗时。
- 首版无需增加模型调用来计算“收益”，避免统计本身引入额外推理成本。

### 后续扩展

- 增加用户主动反馈“这条提醒有帮助”，明确这是主观反馈。
- 支持按项目或引擎筛选，定位不同环境中的记忆使用差异。
- 展示纠正前后的同类记录，帮助用户观察变化，但不自动声称存在因果关系。
- 用固定任务对照评测研究是否减少重复错误。没有对照证据时，不给出“避免了多少错误”或“节省了多少时间”的结论。

### 预期贡献

- **可解释性：** 用户能知道一条记忆何时被使用、移除或纠正。
- **维护决策：** 为修改、缩小范围或归档记忆提供证据，而不只依赖引用次数。
- **性能体验：** 帮助判断记忆准备的额外等待是否值得，并定位耗时来源。
- **项目评估：** 为后续比较记忆策略和引擎行为建立一致的数据口径。

### 验收标准

- [ ] 每个数字有明确含义，并可追溯到对应记录。
- [ ] 用户动作、系统行为和模型判断分开展示。
- [ ] 重试、恢复和重复事件不会重复计数。
- [ ] 区分没有发生、没有数据、审查失败三种情况。
- [ ] 展示统计时间范围与数据覆盖情况。
- [ ] 准备耗时与人工等待分开，不将并行任务耗时直接累加为等待时间。
- [ ] 不把引用或模型审查结果表述为已经证实的实际收益。

## 提交 issue 的建议

1. 每个 issue 先写一个具体使用场景，再描述当前限制和期望行为。
2. 区分已有能力和新增能力，避免把已有功能描述成完全缺失。
3. 将首版范围与后续设想分开，让维护者可以接受其中一个较小的改进。
4. 以验收标准说明完成条件，具体接口和存储设计保留讨论空间。
5. 预期贡献作为设计目标，不写成已经验证的效率提升或效果保证。
